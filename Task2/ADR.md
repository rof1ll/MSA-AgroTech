# ADR-2: Выбор брокера сообщений для событий и телеметрии

# Статус: согласовано

---
## 1. Контекст

В MVP‑версии ИИ‑платформы для отслеживания свиноферм требуется обеспечить стабильный, масштабируемый обмен данными между агентами на фермах (edge‑уровень) и центральной системой.

**По архитектуре предусмотрены:**
- ИИ‑агенты, обрабатывающие видеопотоки и сенсорные данные;
- центральный backend‑кластер (FastAPI‑микросервисы, аналитика, алерты);
- асинхронная передача событий (алерты, телеметрия, статистика, команды управления).

Сообщения должны доставляться надёжно, иметь возможность повторной обработки и гарантировать масштабируемую производительность при увеличении количества edge‑устройств.

**Ключевые цели:**
- Обеспечить стабильную коммуникацию между агентами и облачной платформой при возможных задержках связи;
- Обработку тысяч событий в секунду без потери данных;
- Возможность инференса и аналитики в реальном времени;
- Расширяемость для многоклиентной (multi‑tenant) модели после MVP.

## 3. Решение

#### Варианты решений
1. **RabbitMQ (AMQP 0.9.1)**
    - Простая конфигурация, хорошая документация, поддержка подтверждений доставки.
    - Не предназначен для высоких скоростей ingestion‑логов и потоков IoT‑данных.
    - Ограниченная горизонтальная масштабируемость.
    
2. **NATS / EMQX**
    - Лёгкий, латентность в микросекундах, MQTT‑поддержка.
    - Отлично подходит для edge‑устройств и краткоживущих событий.
    - Нет встроенного долговременного хранения сообщений (нужен JetStream).
    - Ограничен по инструментам аналитического мониторинга.
    
3. **Apache Kafka**
    - Высокая пропускная способность и устойчивость при пиках нагрузки.
    - Хранение событий (commit logs) с возможностью переобработки.
    - Поддержка репликации, ретеншн‑политик и партиционирования.
    - Богатая экосистема (Kafka Connect, Schema Registry, Streams API).
    - Более высокая операционная сложность.
    - Требует стабильных дисковых и сетевых ресурсов.

**Выбранное решение**

Для промышленного контура платформы выбирается **Apache Kafka** в качестве основного брокера сообщений. 
Для пограничного взаимодействия с Edge‑агентами применяется **NATS/EMQX**, который далее ретранслирует потоки событий в Kafka.

*Почему?*
- **Kafka** обеспечивает надёжное хранение сообщений и повторную обработку событий, что необходимо для анализа инцидентов и обучение ML‑моделей.
	
- **Kafka** обеспечивает гарантированную доставку и горизонтальное масштабирование при росте числа агентов
	
- Горизонтальное масштабирование и партиционирование тем позволяют обрабатывать большие объёмы IoT‑данных.
    
- Поддержка Kafka Connect позволяет подключать внешние системы (ClickHouse, BI, ML‑аналитику) без дополнительной разработки.
    
- **NATS/EMQX** оптимален для тонких edge‑агентов, где требуется мгновенная публикация событий.

## 5. Риски

## Риски

- **Технический:** необходимость компетенции DevOps‑команды для эксплуатации Kafka (кластеризация, мониторы lag, tuning).
- **Инфраструктурный:** требует стабильных сетевых каналов и дисков SSD/IOPS > 1000.
- **Организационный:** интеграция NATS→Kafka требует ETL‑прокси‑сервиса.
